#### **PART 5 — EXTRACTED BUSINESS LOGIC AND SKILLS (PLAIN LANGUAGE)**

**Logic 1 — The Complete BLOS Data Architecture (Four Layers)**  
 A BLOS business rule has four layers: (1) `business_rules` — what the rule is (name, description, domain, owner); (2) `condition_logics` — how the rule decides per stage (initial/restore/kill), storing condition expressions in the format `IF GL-metric <op> TH-threshold AND …`; (3) `thresholds` \+ `rule_threshold_mapping` — the numbers the rule uses (threshold values linked to the rule via junction table); (4) `glossary` — what the metric codes in the condition expressions mean (GL-001 \= CTR, etc.). A rule cannot be evaluated without all four layers being complete.

**Logic 2 — Business Code PK Convention**  
 BLOS tables use two different PK types depending on source: human-readable string business codes (`TH-###`, `BL-###`, `MAP-###`, `GL-###`) for entities that are referenced externally and must be stable identifiable IDs; integer auto-increment (`condition_id`, `version_id`) for entities that use plain sequential numbering in the source spreadsheet. Business codes are globally unique, uppercase, and regex-enforced on the server. The format `prefix + zeroPad(max(existing numeric suffix)+1, 3)` generates the next code automatically.

**Logic 3 — The Auto-ID UX Pattern for Non-Technical Data Entry**  
 When a form field requires a globally unique prefixed business code (TH-\#\#\#, BL-\#\#\#, etc.), the correct UX pattern is: auto-generate the next available code on load, display it locked with a 🔒 indicator, show a live availability hint (✓ available / ⚠ duplicate / ⚠ wrong format), and provide an "Edit" toggle for rare manual overrides. The server always normalises (uppercase \+ trim) and validates (regex) regardless of what the UI sends. This prevents malformed codes from non-technical users while allowing expert overrides.

**Logic 4 — Validate-Then-Commit Bulk Import Pattern**  
 Bulk CSV imports must follow a two-phase commit: (1) validate all rows against the same per-record rules as single-add, collect all errors with row numbers, show preview counts (valid / duplicate / invalid); (2) only after the user confirms, commit valid rows inside a transaction — skip duplicates by default, offer upsert as an option. Partial import (valid rows commit even if some rows fail) is correct for bulk operations. This pattern is directly reusable for any admin grid with CSV export.

**Logic 5 — Single-Token Auth and Its Failure Mode**  
 The custom auth system stores one bearer token per user in `user.token` (VARCHAR 60). Each new login generates a new `Str::random(32)` token and overwrites the column. If two people share one account, the second login invalidates the first session's token — `CheckAuthMiddleware` returns 401 on the next API call, `Router.js beforeEach` or `visibilitychange` fires `GET /api/me`, `refreshSessionUser()` returns `'expired'`, auth is cleared, and the user is redirected to `/login`. This appears as "random auto-logout." Resolution: separate user accounts, not multi-session token tables.

**Logic 6 — Build-Alongside Migration Pattern**  
 When replacing a live schema, new tables are built alongside old ones rather than as replacements. Code is migrated to reference the new tables. Old tables are deleted only when they are no longer referenced. This was applied in D01–D03: old tables (`threshold_dependencies`, `threshold_change_requests`, `business_rule_categorical_mapping`) were deleted in D02 when the new schema was live. New tables (`condition_logics`, `business_rules`, `glossary`) were built today. The pattern prevents downtime and allows rollback if the migration fails partway.

**Logic 7 — Manual Deploy Checklist (Fragile Environment)**  
 When deploying to the XAMPP/Linux server with a restricted DB user and no migrations: (1) copy new model files first; (2) `composer dump-autoload`; (3) `php artisan route:clear`; (4) `php artisan optimize:clear`; (5) run DDL SQL as privileged DB account; (6) deploy `public/js/Account.js` (git-ignored, built locally). Skipping step 1 produces `Class App\Models\X not found`. Skipping step 2 produces route 404\. Skipping step 5 as the restricted web user produces `#1142 CREATE denied`.
