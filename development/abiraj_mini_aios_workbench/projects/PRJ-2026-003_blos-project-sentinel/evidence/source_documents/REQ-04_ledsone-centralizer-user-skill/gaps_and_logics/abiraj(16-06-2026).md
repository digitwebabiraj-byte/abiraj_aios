#### **PART 5 — EXTRACTED BUSINESS LOGIC AND SKILLS (PLAIN LANGUAGE)**

**Logic 1 — Why Business Rules Must Reference IDs, Not Display Values**  
 In the old model, a business rule might contain the text "CTR Floor 0.93%" hard-coded in its logic string. If the threshold value changes to 0.90%, the rule text becomes incorrect and must be manually updated across every rule that references it. In the new BLOS model, a rule references `TH-001` — the threshold's business code — and the display value is looked up at render time. Renaming or updating a threshold value propagates automatically to every rule that references it, without any rule text edits. This is why the Rule Builder stores IDs, not values.

**Logic 2 — String Business Code PK Architecture**  
 The new BLOS tables use human-readable string codes as primary keys (`TH-001`, `BL-001`, `MAP-001`). These codes are stable identifiers that remain meaningful across systems, databases, and export/import operations. They are human-auditable in the database without needing to look up an integer ID. The trade-off is that child tables must store these codes in VARCHAR columns rather than integers — requiring child FK columns to be widened when migrating from the old integer-PK model.

**Logic 3 — The Junction Table Pattern for Rule-Threshold Links**  
 In the old model, each threshold row carried `mapping_id` and `rule_id` — linking it directly to its rule. This meant a threshold could only belong to one rule, and querying "which thresholds belong to rule BL-001?" required filtering the threshold table. In the new model, `rule_threshold_mapping` is a separate junction table with rows `(mapping_id, rule_id, threshold_id)`. One rule can map to many thresholds; one threshold can potentially map to many rules. All grouping now requires a JOIN through the junction table rather than a direct column filter on the threshold row.

**Logic 4 — Build Alongside, Retire Later Migration Strategy**  
 When replacing a live database schema, new tables should be created alongside (not instead of) the old ones. Code is migrated to use the new tables. Only after the migration is fully verified are the old tables retired. This prevents any downtime or data loss from a failed migration. The `thresholds` table was an exception — it was replaced in place because the Threshold Configurator needed to keep working — while all other new BLOS tables are built alongside.

**Logic 5 — MySQL `CREATE TABLE IF NOT EXISTS` Permission Nuance**  
 MySQL evaluates the `CREATE` privilege before checking whether the table already exists. A restricted DB user without `CREATE` privilege will receive `#1142 CREATE denied` even when using `CREATE TABLE IF NOT EXISTS` — even if the table already exists and the statement would be a no-op. All DDL must be run from a privileged DB account. Successful phpMyAdmin import output does not always confirm success — verify with `SELECT * FROM <table>` after every import.

**Logic 6 — The Threshold Change Impact Gate Is Unchanged**  
 The governance rule governing threshold value changes survived the schema migration intact: any change touching 2 or more HIGH-impact systems requires a pending approval request; MEDIUM impact requires a `reviewed_impact = true` confirmation; every change requires a reason of at least 10 characters; all changes are versioned. This rule is implemented in `ThresholdConfigurationController@thresholdsUpdate` and operates against the new schema identically to how it operated against the old schema.

**Logic 7 — The BLOS Build Playbook (Per Table)**  
 Repeatable procedure for building any new BLOS table from the Excel model:

1. Read the target sheet with openpyxl  
2. Generate `CREATE TABLE IF NOT EXISTS` \+ `INSERT` SQL — convert literal `"null"` strings to real SQL `NULL`  
3. Run the SQL as a privileged DB account (not `centralizer-limited-web`)  
4. Update the Laravel Model (`$incrementing`, `$keyType`, `$fillable`, `$casts`, relations)  
5. Update the API Controller (validation rules, filter logic, dependency checks)  
6. Update the Vue component (table headers, row cells, form fields, filters, colspan)  
7. Align any child FK columns if the PK type changed (`align_*.sql`)  
8. Rebuild the frontend (`npm run development`)  
9. Deploy code \+ `public/js/*.js`  
10. Verify with `SELECT * FROM <table>`

NEVER insert a duplicate rule-threshold link — UNIQUE(rule\_id, threshold\_id)  
constraint is enforced at the database level  
REASON: a rule must not reference the same threshold twice —  
duplicate links would inflate rule evaluation and UI display
