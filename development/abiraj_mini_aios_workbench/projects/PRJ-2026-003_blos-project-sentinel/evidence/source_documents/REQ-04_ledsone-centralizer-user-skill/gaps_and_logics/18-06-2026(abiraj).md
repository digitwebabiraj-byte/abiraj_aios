#### **PART 5 — EXTRACTED BUSINESS LOGIC AND SKILLS (PLAIN LANGUAGE)**

**Logic 1 — Recursive Tree Model for Rule Logic**  
 A business rule's condition is structured as a tree: a clause is `{metric, operator, value}`; a group joins its children with one operator (AND or OR); the root is always a group. Mixing AND and OR requires nesting one group inside another, which is what produces parentheses in the serialized output. A flat rule is simply a tree with no nested sub-groups.

**Logic 2 — Serialization Guarantees Byte-Identical Round-Trip for Flat Rules**  
 The serializer wraps a child group in parentheses only when that group has more than one child. This means a flat rule (no nested groups) serializes without any parentheses — and re-saving an existing flat rule through parse → serialize produces the exact original string. This was verified by round-tripping all 3 real production BL-001 rules through the new engine and confirming byte-identical output.

**Logic 3 — Three Distinct Identifiers Per Threshold, Each With a Different Purpose**  
 A threshold has three identifiers serving different consumers: `threshold_id` (e.g. `TH-001`) is the value embedded in rule logic and the junction table; `threshold_key` (e.g. `amz_led_uk_organic_ctr_floor`) is the slug used in the YAML export consumed by AI agents and N8N workflows; `label` (e.g. `Organic CTR Floor (Warning)`) is what a human sees in the UI. The Rule Builder shows the label but saves the ID — never the key.

**Logic 4 — Tolerant Parsing, Opaque Output**  
 The rule-logic parser accepts messy real-world input — embedded newlines, irregular spacing, glued operators (`GL-001<TH-001`), and operator aliases — and normalises all of it to a clean, single-line, canonical-operator output on save. Unparseable input never destroys data: it falls back to a raw-text editor rather than failing or silently corrupting the stored string.

**Logic 5 — Code-Existence Validation Prevents Silent Dangling References**  
 Any `GL-###` or `TH-###` code referenced inside a rule's logic string must exist in the live `glossary` or `thresholds` tables at the time the rule is saved. Without this check, deleting or renaming a metric or threshold leaves rules silently pointing at nothing — a dangling reference that produces no error until the rule is evaluated and fails unpredictably downstream.

**Logic 6 — Sticky Table Columns Require Fully Opaque Backgrounds in Every Row State**  
 Any CSS `position: sticky` table column needs a fully opaque background — not a translucent one — applied consistently across normal, even-row, and hover states. A translucent sticky-cell background allows horizontally scrolling row content to visually bleed through the pinned column, corrupting the appearance of action buttons or other pinned UI elements.
